Kibernikto

A multi-agent AI framework with a Telegram body. Built on pydantic-ai and aiogram 3 — run it as a ready bot, or take the bare agent and build your own machine around it.

Two layers, one package. The Telegram transport is optional; the agent is not.

Experts

The parent talks. Experts work.

A credit-tiered parent reaches every specialist through one delegate_task tool. Experts see nothing of the conversation — the parent hands them the exact question, links, dates and language. Errors stay contained.

🌐

web-agent

Live internet: page URLs, news, rates, prices, weather, events. Runs as a tool-less delegate on a search-native model, or as Exa/Researcher tools on the parent when no web model is configured.

🖼

image-agent

Describes, generates and edits images. Picks the real URL off the message automatically — no provider filenames in your prompts.

🏢

Russian companies and sole traders by INN, OGRN, domain or email; address standardization, via DaData. Scoped to the RF, and honest about it.

📞

Telegram peers

Any other bot joins the roster as a sub-agent via TelegramPeerAgent. Correlated answers are admitted automatically — no second env allowlist.

Optional experts load only when enabled, and never as an import side effect. Every expert carries a tool-call limit, so a runaway search loop fails fast instead of burning the parent's credits. Billable experts sit behind CreditGatedSubAgents.

Background delegation

Slow experts stop holding the chat hostage.

A delegation still running after 20 seconds leaves the run. The agent gets an acceptance receipt instead of a result, tells the user the expert is still working, and answers the next message. The report arrives later.

Delegate

The parent calls delegate_task with the full context. Fast work returns normally — nothing changes for the easy cases.

Detach

Past 20s the task moves to the background. The run ends with a receipt, not a fabrication, and the chat stays responsive.

Report

When the expert finishes, its report arrives as a [Background task report] turn and the agent relays it to the user.

Two knobs, both env-only BACKGROUND_AFTER defaults to 20 s, 0 disables detachment entirely. BACKGROUND_MAX caps background tasks per chat at 3.
A saturated chat waits

Rather than queue a fourth, the agent is told to say the others are still working. No silent pile-up.

Reports are data, not orders

The delivered report is wrapped as untrusted content, so a poisoned expert cannot hijack the parent.

Where it refuses to apply

Runs without a conversation_id have nowhere to deliver, so they never detach. Nested delegations report to their parent, and peer envelopes stay foreground.

Restart is honest

Running background tasks do not survive a process restart. Don't build billing on top of them.

Opt-in per call

The parent can pass background=True for work it already knows is slow, instead of waiting out the timer.

Credits & tiers

Your balance picks the model.

Not a plan, not a prompt — a conversation's credit balance decides which model answers, and the tier is pinned for the whole run. Spending down changes the model mid-relationship, quietly and on purpose.

poor

< 30 credits

The cheap model keeps the chat alive. Default gemini-2.5-flash, and everything still works.

medium

30 – 499 credits

The normal model. The one you configured, with fallbacks in priority order behind it.

rich

≥ 500 credits

Top tier. The same configuration carries you here — and unlocks credit-gated experts that stay hidden on lower balances.

Charged after success, never before

One credit per successful run by default, plus a credit per successful delegate_task. Failed runs are free. Voice replies cost double.

Top-ups are Telegram Stars

One Star, one credit. Users run /balance and /pay; admins can /pay <credits> <tg_id> to grant or deduct.

At zero, a policy decision

ALLOW_ZERO_CREDITS=true drops the chat to the poor tier. Set it to false and billable runs are blocked with a top-up hint instead.

Subscriptions are separate

Star subscriptions and credit gating are independent checks. Neither one silently overrides the other.

Logfire & storage

Traces you can query. History you can swap.

Logfire is not a sidecar here. It instruments every agent, model and tool call — and it can also be the history store.

logfire.instrument_pydantic_ai()
Every call is a span. Agents, models, tools — with tool arguments in gen_ai.tool.call.arguments, not smeared across your console.
APP_STORAGE_DATA_BACKEND
file, sqlite, pg, logfire. The first three are ordinary stores. logfire rebuilds conversation history from traced all_messages spans — read-only, and your observability becomes your transcript.
APP_STORAGE_MEDIA_BACKEND
file or s3. Bucket credentials are checked with a HEAD before polling starts: an unreachable bucket crashes the bot at boot, not at the first voice message.
APP_LOG_CONSOLE
stdlib or logfire. Either our formatted records beside the span lines, or one merged Logfire timeline. Your choice of what the operator sees.
APP_LOG_HTTP
Raw provider request and response bodies. Noisy, and it may contain user content. Useful for a bad afternoon, wrong for production.
APP_STORAGE_HISTORY_WINDOW_SLACK
Why SQL history still reads correctly. The tail fetch reads a slack multiple of the window and walks back to a request boundary — deliberate, not a bug to tidy up.

Architecture

Four layers. No inheritance chain to untangle.

There is no agent superclass. You compose capabilities onto a plain pydantic_ai.Agent and hand it whatever transport you like.

CLI
The kibernikto command. Reads a single env file, starts the process. One process per bot token — no exceptions, no shared pollers.
telegram
aiogram dispatcher. Conversation handlers, a middleware chain (Peer → Service → Firewall → Subscription), pre-processors for text, photo, voice and audio, and Telegram Stars payments.
ai.agent
The brain. build_kibernikto_agent() returns a plain Agent with ConversationHistory and PersonaCapability. Addons hang off the side.
storage
One contract, several backends. History and chat data in files or SQL; media in files or S3. Swapped by environment, not by refactor.

Build

Take the agent. Leave the bot.

No Telegram required. The core builder gives you a standard pydantic-ai agent with Kibernikto's memory and persona already attached.

your_app.py 
from kibernikto.ai.agent import build_kibernikto_agent

# Just a pydantic_ai.Agent — history and persona are capabilities, not a subclass.
agent = build_kibernikto_agent(
    model="openrouter:anthropic/claude-sonnet-5",
    history_size=40,
)

result = await agent.run(
    "remind me what we decided about storage",
    conversation_id="thread-42",   # per-conversation history
)

print(result.output)                # AgentRunResult — .output, not .data
openrouter: vsegpt: routerai: beget: or any pydantic-ai model string

New OpenAI-compatible gateway? It's one OPENAI_COMPATIBLE_PROVIDERS entry in kibernikto/ai/agent/utils.py. Everything else falls through to pydantic_ai.infer_model.

Deploy

From clone to systemd in two scripts.

Run the bot

Fill in TG_BOT_KEY, TG_MASTER_ID and one provider key.

# one process per bot token
kibernikto --env_file_path=kibernikto.env
kibernikto --env_file_path=kibernikto.env \
  --multi-agent

Run the server

deploy/ is a ready layout: podman + systemd, one folder per bot.

deploy/scripts/rebuild.sh -b kibernikto
deploy/scripts/update.sh
  • Dockerfiles default to --multi-agent
  • Zero-credit chats fall back to the cheap model
  • Backups and rollback in the runbook
